## ۱. هدف

این رویه مشخص می‌کند وقتی کارکرد یک صفحه موقت به پایان رسید، چگونه آن صفحه به‌صورت کنترل‌شده بازنشسته شود، صفحه اصلی سایت دوباره در دسترس قرار گیرد، داده‌ها حفظ شوند و تمام تغییرات در GitHub و اسناد پروژه ثبت شوند.

## ۲. فرمان توافق‌شده

هر زمان مالک عبارت دقیق زیر را ارسال کند، آن را به‌عنوان درخواست شروع فرایند بازنشسته‌سازی صفحه موقت تفسیر کن:

`PLATO LAND – CLOSE PAGE`

این عبارت یک فرمان کاری است، نه مجوزی برای حذف اطلاعات یا تغییرات نامرتبط.

### تعیین صفحه هدف

- اگر فقط یک صفحه موقت فعال و در حال استفاده باشد، همان صفحه هدف است.
- اگر بیش از یک صفحه موقت فعال باشد یا هدف از متن گفتگو روشن نباشد، پیش از هر تغییر اجرایی فقط یک سؤال کوتاه برای مشخص‌شدن صفحه هدف بپرس.
- صفحه‌های دائمی سایت، پنل مالک، مسیرهای مدیریتی یا قابلیت‌های دیگر نباید صرفاً به دلیل شباهت نام یا ارتباط با صفحه موقت غیرفعال شوند.
- صفحه اصلی سایت باید پس از بازنشسته‌سازی در مسیر اصلی خود قابل نمایش بماند.

## ۳. اقدامات الزامی پس از دریافت فرمان

### ۳.۱ بررسی پیش از تغییر

1. آخرین وضعیت پروژه، شاخه `main`، commitها، Pull Requestها و workflowهای مرتبط را بررسی کن.
2. مستندات جاری، گزارش ایجاد صفحه و تصمیم‌های تأییدشده مالک را مطالعه کن.
3. مسیر عمومی صفحه هدف، مسیرهای وابسته، APIها و Edge Functionهای مرتبط را شناسایی کن.
4. محل نگهداری داده‌ها و وابستگی‌های صفحه را مشخص کن.
5. دامنه تغییر را محدود و قابل بازبینی نگه دار؛ از بازنویسی یا پاک‌سازی نامرتبط خودداری کن.

### ۳.۲ غیرفعال‌سازی صفحه

1. دسترسی عمومی به صفحه موقت هدف را ببند یا مسیر آن را به صفحه اصلی بازگردان؛ روش باید با معماری فعلی سایت سازگار باشد.
2. اگر صفحه از endpoint، API یا Edge Function برای دریافت داده استفاده می‌کند، مسیر ثبت جدید را نیز در صورت نیاز و با حفظ دسترسی‌های لازم به‌طور امن متوقف کن.
3. صفحه اصلی سایت را در مسیر اصلی حفظ کن و از تغییر محتوای آن خودداری کن.
4. مسیرهای مدیریتی دائمی یا گزارش مالک را فقط در صورتی تغییر بده که صریحاً بخشی از دامنه مورد توافق باشند.
5. از باقی‌ماندن راه فرعی برای ارسال داده جدید به قابلیت بازنشسته‌شده جلوگیری کن؛ این موضوع باید با آزمون مناسب بررسی شود.

### ۳.۳ حفاظت از اطلاعات — الزام غیرقابل‌مذاکره

- هیچ رأی، درخواست ثبت‌نام، Plato ID، تصویر، نتیجه، رکورد یا سابقه‌ای صرفاً برای بستن صفحه حذف نشود.
- جدول‌ها، رکوردها، Storage، تاریخچه و گزارش‌های موجود حفظ شوند.
- هیچ جدول یا دیتابیس جدیدی برای بازنشسته‌سازی ساخته نشود.
- دیتابیس اصلی Supabase همان پروژه موجود است؛ دیتابیس preview/test یا محیط جداگانه ایجاد یا استفاده نشود.
- هرگونه تغییر دیتابیس باید ضرورت مستقل، دامنه روشن و مجوز صریح مالک داشته باشد. بستن صفحه به‌خودی‌خود مجوز حذف یا تغییر داده‌ها نیست.
- در گزارش نهایی دقیقاً مشخص کن آیا دیتابیس، جدول‌ها، رکوردها، Storage یا Edge Functionها تغییر کرده‌اند یا خیر.

### ۳.۴ ثبت تغییرات و انتشار

1. تغییرات را در شاخه کاری جداگانه و با کمترین فایل لازم انجام بده.
2. تغییرات را بازبینی کن و TypeScript/Build و آزمون‌های مرتبط را اجرا کن.
3. برای ادغام به `main` و انتشار production فقط از روند کنترل‌شده GitHub پروژه استفاده کن.
4. هیچ‌گاه صرفاً از موفقیت Build نتیجه نگیر که انتشار یا آزمون واقعی مرورگر موفق بوده است.
5. وضعیت PR، merge commit، workflow انتشار و پاسخ دامنه زنده را جداگانه گزارش کن.
6. اگر انتشار یا تست مستقل قابل انجام نیست، آن را صریحاً «تأییدنشده» اعلام کن؛ ادعای انجام قطعی نکن.

## ۴. مستندسازی الزامی

برای هر صفحه موقت، یک گزارش مستقل بازنشسته‌سازی در پوشه `docs/` ایجاد یا تکمیل کن. گزارش باید دست‌کم شامل این موارد باشد:

- نام صفحه و هدف آن
- مسیر/URL عمومی و مسیرهای مدیریتی مرتبط
- تاریخ ایجاد و تاریخ بازنشسته‌سازی، در صورت موجودبودن شواهد
- علت و دستور مالک برای بستن صفحه
- PRها، commitها و فایل‌های تغییرکرده
- تغییرات مسیرها، APIها و Edge Functionها
- وضعیت دیتابیس و Storage
- تعداد و وضعیت داده‌های حفظ‌شده، فقط بر پایه Query یا شواهد واقعی
- نتایج Build، TypeScript، تست‌ها و بررسی مرورگر
- وضعیت Deploy و مشاهده دامنه زنده
- موارد باز یا تأییدنشده
- چک‌لیست نهایی حفاظت از داده‌ها

همچنین این اسناد مرجع، در صورت ارتباط، به‌روزرسانی شوند:

- `docs/TECHNICAL_HANDOVER_*.md`
- `docs/PROJECT_HISTORY_AND_TECHNICAL_DOCUMENTATION_*.md`
- Implementation Register و QA Checklist معتبر پروژه
- README یا فهرست اسناد، اگر به گزارش جدید ارجاع می‌دهند

از ایجاد نسخه‌های موازی و متناقض خودداری کن؛ ابتدا فایل مرجع موجود را پیدا و همان را به‌روزرسانی کن.

## ۶. قالب گزارش نهایی به مالک

گزارش نهایی باید این موارد را جداگانه اعلام کند:

1. **کد:** چه فایل‌هایی تغییر کردند؟
2. **دیتابیس و داده‌ها:** آیا تغییری انجام شد؟ چه داده‌هایی حفظ شدند؟ شواهد چیست؟
3. **آزمون:** TypeScript، Build، تست عملکرد و تست مرورگر هرکدام چه وضعیتی دارند؟
4. **انتشار:** PR، merge commit و workflow انتشار چه نتیجه‌ای داشتند؟
5. **سایت زنده:** آیا بازگشت صفحه اصلی مستقلاً بررسی شده یا فقط مالک آن را مشاهده کرده است؟
6. **مستندات:** کدام گزارش‌ها و اسناد به‌روزرسانی شدند؟
7. **موارد باز:** چه چیزی هنوز تأیید یا آزمایش نشده است؟
